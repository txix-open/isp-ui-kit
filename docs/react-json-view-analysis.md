# ReactJsonView: анализ legacy и варианты перехода

Дата: 8 октября 2026 года. Это анализ и предложение следующего шага, а не выполненная миграция. Компонент и зависимости пока не изменены.

## Принятое решение — 9 октября 2026 года

По решению пользователя ReactJsonView остаётся отдельным legacy-компонентом без изменений логики, оформления, API и зависимостей. Он исключён из редизайна. Описанные ниже варианты перехода и прототипы не входят в текущий план; анализ сохранён только для справки.

## Вывод анализа до принятого решения

Первым кандидатом для перехода стоит проверить `@microlink/react-json-view`: он сохраняет происхождение и большую часть API нашей копии. Прямая замена потеряет переименование ключей и редактирование объекта/массива целиком. Эти возможности нужно выделить в отдельный контракт и перенести осознанно.

Предпочтительный путь: прототип Microlink рядом с текущим компонентом, проверка совместимости, затем решение между внешней обёрткой и небольшим сопровождаемым форком. Текущий публичный экспорт сохраняем до доказанной совместимости. Не стоит переписывать всё дерево с нуля только ради нового оформления.

## Что поддерживаем сейчас

В `src/components/ReactJsonView` находятся 36 файлов исходников и стилей, около 3950 строк вместе с декларациями. Реализация — JS/JSX на классах; TypeScript-декларация поддерживается отдельно. Она уже расходится с реализацией: нет `editKeys`, описанный default группировки массивов — 100, фактический — 1000.

Компонент экспортируется из основного entry point. В этом репозитории найден только пример Storybook; это не доказывает отсутствие потребителей в приложениях. Единственная история не покрывает отказ callback, переименование, замену вложенного объекта и несколько экземпляров.

Сложность создают не только стили: глобальный dispatcher, singleton-хранилище, рекурсивные компоненты, отдельные редакторы и модальные окна, ручное копирование ветвей объекта и inline-темы Base16. `lodash` импортируется здесь, но отсутствует в объявленных зависимостях пакета. Сейчас он доступен транзитивно.

## Различия с Microlink

Сравнение выполнено с исходниками ветки `master`, скачанными 8 октября 2026 года; в её `package.json` указана версия 1.31.38. Это версия манифеста ветки, а не проверка последнего опубликованного npm-релиза. Форматирование файлов нормализовано перед сравнением.

| Сценарий | Наша версия | Microlink master | Что сохранить при переходе |
| --- | --- | --- | --- |
| Переименование ключа | `editKeys`, отдельный `EditKeyRequest`; ключи примитивов и объектов | Аналогичных действий в просмотренных исходниках нет | Права на переименование, callback, поведение при конфликте |
| Конфликт имени при переименовании | Создаётся ключ `${key_name}-copy`; старый удаляется | Переименования нет | Явно описать конфликт, включая уже существующий `-copy` |
| Замена объекта/массива целиком | Textarea, определение типа, подтверждение и отмена, `object_update` | В компоненте Object аналогичного редактора нет | Замена корня и вложенной ветви без изменения соседей |
| Действия у объекта | При раскрытии рядом с открывающей скобкой; при сворачивании рядом с закрывающей | Иное расположение метаданных | Проверить плотность и доступность действий |
| Группировка массивов | Default 1000 | Default 100 | Передавать старое значение явно в совместимом API |
| Порядок массивов | `variables.sort()` во время построения дочерних строк | Такой сортировки нет | Сохранять исходный порядок; мутацию не переносить |
| Расширения просмотра | Часть новых параметров отсутствует в реализации | Есть `showComma`, `escapeStrings`, `displayArrayKey`, `bigNumber`; защита рекурсии от циклов | Проверять отдельно, не считать обязательными legacy-функциями |

Переименование примитивных ключей у нас дополнительно скрыто для имён, приводимых к числу. Переименование ключей объектов проверяет `editKeys`, но не проверяет `onEdit` в месте создания действия. Это неоднородность прав доступа, а не желательная особенность нового API.

Источники: [Microlink README](https://github.com/microlinkhq/react-json-view), [корневой компонент](https://github.com/microlinkhq/react-json-view/blob/master/src/js/index.js), [Object](https://github.com/microlinkhq/react-json-view/blob/master/src/js/components/DataTypes/Object.js), [ObjectAttributes](https://github.com/microlinkhq/react-json-view/blob/master/src/js/stores/ObjectAttributes.js), [манифест](https://github.com/microlinkhq/react-json-view/blob/master/package.json).

## Обнаруженные проблемы

Первые четыре пункта проверены запуском фактических классов и хранилища через Babel в Node. Это проверка логики, без монтирования React в браузере.

1. **Отображение изменяет исходный массив.** `Object.renderObjectContents` сортирует переданный массив на месте, независимо от `sortKeys`. Вход `[2, 10, 1]` становится `[1, 10, 2]`. На `Object.freeze([2, 10, 1])` возникает исключение. Это изменение данных пользователя при чтении.
2. **Отказ `onEdit` не откатывает хранилище.** Для `{a: 1, b: 1}` отклоняем `a → 9`: экран сохраняет старое значение, store уже содержит 9. Последующее разрешённое `b → 2` возвращает `{a: 9, b: 2}`. Отклонённое изменение попадает в результат следующей операции.
3. **Замена вложенной ветви с точкой в имени может менять другой путь и входной объект.** Для `{'a.b': {nested: {x: 1}}, a: {b: {nested: {x: 2}}}}` запрос замены `['root', 'a.b', 'nested']` меняет `a.b.nested`, а не литеральный ключ `'a.b'`. В этой проверке меняется и исходный `src`: копирование использует сегменты, `lodash.set` — строку с точками.
4. **Состояния раскрытия могут пересекаться.** Namespace `['root', 'a,b']` и `['root', 'a', 'b']` превращаются в одинаковый ключ объекта хранилища. Запись для одной ветви меняет значение другой.
5. **Store сохраняет данные после unmount.** Listener удаляется, запись `objects[rjvId]` остаётся. Это подтверждено вызовом lifecycle; рост памяти приложения требует отдельного профилирования.
6. **Идентификатор — только `Date.now()`.** При одинаковом времени два экземпляра получают одинаковый ID; проверено с фиксированным временем. Частоту реальных столкновений не измеряли.
7. **Доступность требует отдельной работы.** Действия построены на SVG/div/span; окно ключа не реализует полноценное управление фокусом диалога. Копирование использует `document.execCommand` и не проверяет успешность операции.

Microlink добавляет случайную часть ID и не содержит нашей сортировки массива. Однако по сравнению исходников в нём остаются singleton-store, глобальный dispatcher, запись `updatedSrc` в store до проверки callback и отсутствие очистки записей при unmount. Его нельзя считать автоматически исправленной заменой. Одновременная загрузка нашей копии и Microlink также требует проверки: оба используют `globalThis.__globalDispatcherInstance`, а регистрация заменяет единственный handler.

## Варианты реализации

### 1. Стабилизировать текущий компонент

Исправить мутацию массивов, отказ до commit, операции по массиву сегментов, очистку и идентификаторы. Синхронизировать типы, права действий и зависимости. Это самый прямой путь для срочных исправлений, но он сохраняет почти весь объём сопровождаемого кода.

### 2. Microlink плюс наши расширения — основной кандидат

Внешняя обёртка подходит для defaults, темы, callback и дополнительных действий вне дерева. Для сохранения прежних inline-действий простого проброса props недостаточно: в просмотренных исходниках нет подходящего публичного слота для замены редактора узла. DOM-инъекции и обращения к приватному store слишком хрупки.

Практичные варианты: согласовать расширение API с upstream либо вести форк с явно выделенными изменениями. Форк имеет смысл, если разница ограничена нашими редакторами и исправлениями, а обновления upstream можно регулярно проверять. Постоянное копирование всей библиотеки в кит повторит текущую проблему.

Для редакторов переименования и замены ветви нужен общий типизированный модуль операций: сегментированный путь, неизменяемый результат, валидация перед commit. UI отдельно: Ant Design Input/Modal или наш CodeEditor для JSON-ветви. Monaco — возможный редактор текстового режима, но не замена дереву и не универсальный сериализатор Date, undefined, NaN, функций и RegExp.

### 3. Другой движок

[json-edit-react](https://github.com/CarlosNZ/json-edit-react) — резервный кандидат для прототипа: редактирование, ограничения действий и обработка изменений есть, но API существенно отличается. Нужно адаптировать события и проверить типы данных, тему, клавиатуру и стоимость зависимости.

[@uiw/react-json-view](https://github.com/uiwjs/react-json-view) также имеет отдельное расширение редактора; просмотренный манифест v2 указывает alpha-версию, поэтому нужна проверка готовности конкретного релиза. [@textea/json-viewer](https://github.com/TexteaInc/json-viewer) требует Material UI/Emotion; для нашего Ant Design кита это менее подходящий первый выбор.

## Возможные шаги при пересмотре решения (сейчас не планируются)

1. Добавить истории текущего компонента: readonly, edit/add/delete, переименование, конфликт, замена корня и ветви, отказ callback и следующая операция, внешний reset, несколько экземпляров, необычные ключи и массивы. Сначала зафиксировать контракт; известные ошибки не делать эталоном совместимости.
2. Сделать отдельный прототип на зафиксированном опубликованном Microlink-релизе. Проверить React 18/19, StrictMode, ESM/сборку, темы, clipboard, отсутствие пересечения dispatcher и две наши дополнительные операции. Измерить сборку и отзывчивость на 1000/10000 узлов.
3. По результатам выбрать обёртку с отдельными действиями либо небольшой upstream-форк. Задокументировать изменения UX и контракт событий, сохранить имя экспорта и значения defaults для старых потребителей.
4. Переключать основной экспорт только после проверки приложений-потребителей. Старые зависимости удалять после поиска использования во всём ките. PcsKit не менять.

Критерий успеха — сохранены нужные действия и API, данные не мутируют при просмотре, отказ действительно блокирует изменение, а поддерживаемая нами часть стала заметно меньше.
