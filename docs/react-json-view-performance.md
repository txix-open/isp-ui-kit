# ReactJsonView: производительность на больших данных

Дата: 30 октября 2026 года. Продолжение работы над `src/components/JsonViewer` (публичный экспорт `ReactJsonView`; дизайн-документ переписывания — `docs/react-json-view-rewrite.md`). Цель: компонент работает на данных ~10 000 строк без деградации, редактирование (onEdit/onAdd/onDelete) при этом сохраняет поведение.

## Проблема

Обычный (не виртуализованный) режим рендерит всё видимое дерево: раскрытый массив из 10 000 элементов даёт десятки тысяч DOM-узлов. На таких данных рендер, сворачивание и скролл становятся неприемлемо медленными.

Решение сделано тремя фазами: (1) quick wins — убрать лишние перерисовки в обычном режиме; (2) виртуализация — новый опциональный режим по `maxHeight`; (3) поиск — опциональный `search` c авто-раскрытием и подсветкой, работающий в обоих режимах.

## Фаза 1: быстрая оптимизация (обычный режим)

- **Версионные подписки на флаги store.** `ViewerStore` хранит на каждый ключ (вид `flag:namespaceKey`) свой версионный номер; `useStoreFlag` подписывается через `useSyncExternalStore` на версию конкретного ключа. Смена флага одного узла не перерисовывает остальных (вместо глобальной подписки на всё дерево).
- **Мемоизированные actions и контекст.** `actions` (`useMemo`, зависимость — `commit`/колбэки/store) и объект контекста стабильны до изменения входных данных; подписчики `useViewer` не перерисовываются на каждом рендере зрителя.
- **`React.memo` на строках и узлах.** `Node`, `VariableRow`, `ObjectName`, `DataTypes` (JsonString/JsonInteger/JsonFloat/JsonBoolean/JsonNull/JsonDate и др.) мемоизированы; сравление `Node` — по содержимому namespace (`sameSegments`), а не по identity массивов.
- **`content-visibility: auto`** на `.variable-row` (scss) — браузер прокладывает отрисовку строк вне области видимости. В виртуализованном режиме отключается (`.react-json-view.rjv-virtual .rjv-row { content-visibility: normal }`) — окно отрисовки и так ограничено.

Результат: обычное дерево (сотни–тысячи строк) сворачивается/раскрывается без перерисовки соседей; регрессия проверена по baseline-скриншотам (см. отчёт).

## Фаза 2: виртуализация (`maxHeight`)

### Публичный API

```ts
/** Высота контейнера в px. Если задано, включается виртуализованный режим. */
maxHeight?: number;
```

Добавительно, существующие props не меняются. Режим определяется в `JsonViewer` как `props.maxHeight !== undefined` и раздельно рендерит `VirtualTree` (виртуальный) или `Tree` (обычный).

### Архитектура

- **Плоское представление — `flattenTree` (`virtual/flatten.ts`).** Дерево разворачивается в плоский массив строк `FlatRow` с фиксированными kind: `node-open`/`node-collapsed`/`node-close`, `value`, `array-group-header`, `group-open`/`group-open-collapsed`/`group-collapsed`/`group-close`. Строка несёт все данные рендера (`BranchRowData`/`ValueRowData`/`GroupRowData`) — рендер строки не зависит от дерева. Перестроение списка — при смене `src`, настроек, `searchExpandKeys` или глобальной версии store (любая смена флага).
- **Окно отрисовки — `VirtualTree` (`virtual/VirtualTree.tsx`).** Скролл-контейнер `.rjv-scroller` (`max-height: maxHeight px; overflow-y: auto`); высота внутреннего спейсера — `rows.length × rowHeight`. Отрисовывается только `rows.slice(start, end)`, где `start/end` — от `scrollTop`/`viewport` с запасом `OVERSCAN = 12` строк с каждой стороны. `scrollTop` читается по `requestAnimationFrame` (без дребезга на каждый скролл-событие); `viewport` — через `ResizeObserver`.
- **Высота строки.** Строки однострочные (см. ниже) и все одинаковой высоты: меряется `offsetHeight` первой отрисованной строки (`useLayoutEffect`), до измерения используется `ROW_HEIGHT_FALLBACK = 26`.
- **Рендер строки — `FlatRow` (`virtual/FlatRow.tsx`).** Строка — абсолютно позиционированный `div.rjv-row` (`top: index × rowHeight`), вложенность — не вложенными div'ами, а вертикальными направляющими `.rjv-guide` (1px-линии по координатам `M + S·i`, `S = 27px` на уровень, `M = 6px` — геометрически 1:1 с обычным режимом). Левый отступ — `padding-left: var(--rjv-pl)` (CSS), при hover `padding-left` уменьшается на 1px и собственная направляющая расширяется до 2px (тоже CSS, через кастомное свойство).
- **Однострочные значения.** Виртуальный режим требует фиксированной высоты строки: значения не переносятся (`nowrap`, `ellipsis`, полный текст в `title`). Длинные значения дополнительно показываются в overlay-подсказке при клике на строку (`.rjv-overlay-text`), а редактирование — в overlay-редакторе (`.rjv-overlay`). Overlay привязан к строке по её стабильному ключу (`flatRowKey`), закрывается, когда строка покидает окно отрисовки, по клику вне себя и (для текстового) по Escape.
- **Редактирование.** Те же `actions` store (`editVariable`/`editBranch`/`requestAddKey`/`requestRenameKey`/`removeVariable`) — коммит, валидация (отказ callback → баннер `validation-failure`) и payload-ы совпадают с обычным режимом. Разница только в носителе: вместо инлайнового textarea — overlay над строкой; значение в строке остаётся однострочным (в DOM длинный текст усекается, полный — в overlay).
- **Классы.** Новый DOM-набор: `.rjv-virtual` (на том же корневом элементе `.react-json-view` — стили виртуального режима пишутся только составным селектором `.react-json-view.rjv-virtual { ... }`), `.rjv-scroller`, `.rjv-row`, `.rjv-row-content`, `.rjv-guide`/`.rjv-guide--own`, `.rjv-overlay`, `.rjv-overlay-text`, `.search-match`. Старые классы (`variable-row`, `object-key-val`, …) в виртуальном режиме не используются, за исключением `variable-row` как маркера строки.

### Состояние групп в виртуальном режиме

Раскрытие групп длинных массивов хранится в store отдельным видом флага `groupExpanded` (ключ — `namespaceKey([...namespace, groupIndex])`), а не в локальном состоянии `ArrayGroup` — потому что `VirtualTree` перестраивает плоский список вне иерархии React-компонентов и локальное состояние групп было бы недостижимым. Поведение (группы свёрнуты по умолчанию, содержимое группы подчиняется флагу `expanded` массива) совпадает с обычным режимом.

## Фаза 3: поиск (`search`)

### Публичный API

```ts
/**
 * Запрос поиска. Узлы, чей ключ (объектов) или примитивное значение
 * содержит запрос (без учёта регистра), автоматически раскрываются
 * (сохранённый флаг раскрытия имеет приоритет), а текст вхождений
 * подсвечивается. Работает в обоих режимах (с maxHeight и без).
 */
search?: string;
```

### Индекс совпадений — `utils/search.ts`

`buildSearchIndex(src, rootSegment, search)` возвращает `ReadonlySet<string>` — **абсолютные namespace-ключи предков** совпавших узлов (сами совпадения-контейнеры в индекс не входят: их строка видна, когда раскрыт родитель). Пересчитывается в `JsonViewer` (`useMemo` по `committedSrc`/`rootSegment`/`search`), передаётся через контекст как `searchExpandKeys` (`null`, когда `search` не задан или пуст).

Совпадают (регистронезависимое подстроковое вхождение):

- **имена ключей объектов** — все ключи, включая ключи с примитивными значениями (индексы массивов как ключи не считаются совпадением — это шум);
- **строковые представления примитивных значений** (`stringifyVariable`).

**Двойная форма ключей.** Внутренние namespace-ключи — JSON-сериализация массива сегментов, и для индексов массивов сегмент имеет **разный тип в разных режимах**: обычный режим строит namespace строками из `Object.keys` (`["a","logs","0"]`), виртуальный (группы) — числами (`["a","logs",0]`). Индекс поэтому содержит для каждого сегмента-индекса обе формы: walk идёт с числовым сегментом для детей массивов, а `addKey` дописывает «двойника» со строковым (`["a",5]` → `["a","5"]`). Флаги раскрытия в обоих режимах находят свою форму.

### Авто-раскрытие

- **Узлы.** В обоих режимах правило одно (Node — `defaultExpanded || searchAuto` как дефолт `useStoreFlag`; flatten — `nodeExpanded`): сохранённый флаг пользователя в store имеет приоритет; иначе узел раскрыт, если `defaultExpanded` (по `collapsed`/`shouldCollapse`/пустоте) **или** его ключ в индексе поиска.
- **Группы массивов.** Группа раскрывается автоматически, если содержит совпадение (какой-либо ключ элемента группы в индексе; проверка — `childNamespaceKey(namespaceKeyStr, i)` по диапазону группы, без переобхода дерева). В обычном режиме группа — локальное состояние `expandedGroups[i]` в `ArrayGroup` (дефолт `?? searchGroupOpen(i)`, теггл — по видимому состоянию), в виртуальном — флаг store `groupExpanded` (дефолт `stored ?? searchWants`).
- **Строки значений** (примитивы внутри раскрытого родителя) и ключи контейнеров получают подсветку.

### Подсветка

`components/Highlight.tsx` — общий компонент: regex-сплит текста по запросу (без учёта регистра), все вхождения оборачиваются в `<span class="search-match">`. Применяется в `ObjectName` (ключ), `JsonString`/`JsonInteger`/`JsonFloat` (значения) и в инлайновом рендере ключа строк (VariableRow и FlatRow). Стиль `.search-match` — в `getStyle` (`backgroundColor: colors.dataTypes.background`, `borderRadius: 2px`, `padding: '0 1px'`).

## Осознанные отклонения

- **Виртуальный режим — однострочные строки** фиксированной высоты: длинные значения усекаются (`ellipsis` + `title` + overlay); обычный режим — многострочные (как в legacy).
- **Вложенность в виртуальном режиме** — направляющие (`.rjv-guide`) по координатам, а не вложенные div'ы с padding'ами (обязательное условие фиксированной геометрии).
- **Состояние групп** — в store (`groupExpanded`) в виртуальном режиме, локально в `ArrayGroup` в обычном (см. выше); поведение идентично.
- **Пустое имя нулевого индекса** — сохранено 1:1 за legacy: `display_name = name ? name : ''` — нулевой элемент массива рендерится без имени в обоих режимах.
- **Поиск — это не «найти и перейти»**: без авто-раскрытия совпадения были бы скрыты в свёрнутых контейнерах; явного «пересколла к совпадению» нет (первый видимый совпадающий узел пользователь докручивает сам — или раскрывает вручную).
- **Storybook 10 блокирует `args` из URL** («Omitted potentially unsafe URL args»): story `LargeData` использует дефолт `search={args.search ?? 'latency'}` — без дефолта поиск в этой story не продемонстрировать.
